# Agent Note: 单一开关下的自动视觉路由

Status: implemented

[English](2026-08-20-automatic-visual-routing.md) | 中文

## Problem

Desktop 已经提供兼容视觉旁路，而 Harness rc.8 又为具备能力的对话模型增加了原生图片输入。如果两套机制分别暴露，用户会面对含义重叠的控制项，同一张图片也可能同时进入主要模型与旁路。当前模型本身可以接收图片时仍要求配置兼容提供方 Key，也会增加没有必要的门槛。

## Decision

输入区只保留一个面向用户的 `视觉增强` 开关。开启后，系统为当前提供方与模型选择且只选择一条路径：只有确切模型元数据包含 `image` 时才使用原生图片输入；否则使用已经验证的百炼或 OpenRouter 旁路。没有声明图片能力且没有可用兼容提供方的模型进入 `unavailable`，系统打开既有提供方配置，而不是接收图片。

Host 通过 `vision.route` 与原子操作 `vision.activate` 持有路由决定。启用原生路径时只写入开启设置，不要求视觉提供方凭证；启用兼容路径时必须存在已经配置且完成验证的提供方。客户端读取当前 Session 经 Host 接受的模型选择，并显示 `原生` 或 `兼容 · 提供方`；模型变化后重新计算标签，不增加第二个模式选择器。DeepSeek 模型编辑器中的“允许原生图片请求”只是单个模型的能力声明，并不是路由控制，因此私有或后续新增的视觉模型也能为同一套自动决策提供明确元数据。

在 LLM 边界，原生路径只把包含原图的请求向下委托一次。兼容路径继续把图片块替换成现有的持久视觉观察，不再发送原图。开关关闭时，新图片 Prompt 会在附件持久化前被拒绝；历史图片块则被替换成明确的模型可见省略标记，界面与持久附件历史本身保持不变。

本决策把[直接 DeepSeek 视觉输入](2026-08-19-direct-deepseek-vision-input.md)的确切模型原生能力，与[可选择视觉提供方](2026-08-16-selectable-visual-providers.md)中已经验证的旁路组合起来。它不改变提供方凭证、模型选择、附件存储，也不改变设置弹窗中的兼容提供方配置。

## Alternatives considered

**提供“自动、原生、Qwen 兼容、关闭”四种模式。** 不采用：原生和兼容是由模型能力决定的实现路径，不是彼此独立的用户目标。模式菜单会重复模型选择器与提供方设置，还会允许用户选择实际无法运行的组合。

**开启后始终运行兼容视觉旁路。** 不采用：具备原生能力的模型只能收到文字观察而非原图；如果随后再发送原图，还会造成重复处理、额外延迟和提供方费用。

**始终把图片发给当前对话模型。** 不采用：明确只支持文本的模型需要已经验证的兼容路径，否则 Prompt 接受后仍会失败。

**开关关闭时仍允许原生图片。** 不采用：唯一可见开关必须控制完整产品能力。如果界面显示关闭但原生图片仍进入模型，界面状态就是错误的。

## Consequences

用户只需启停一个能力，使用原生视觉模型时无需配置 Key。切换模型后实际路径可能变化，因此输入区会显示当前路径，Host 也会在 Prompt 准入与流调用时重新检查。自动原生路由有意以明确证据为准：未声明模态的适配器会使用兼容路径，只有声明 `image` 后才会收到原始图片块。关闭功能会阻止模型读取图片，但不会删除附件或重写 Session 历史。
