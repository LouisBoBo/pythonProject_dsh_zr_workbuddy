### 2.3 审码质量与体验：一轮轮踩坑 → 定型

| 现象（用户反馈） | 根因（摘要） | 处理 |
|------------------|--------------|------|
| 无过程 / 无报告 / 卡在确认界面 | 流式编排、进度与终稿未打通 | 确认卡 → `POST …/run/stream`；进度卡 + 终稿 |
| 报告像「分批纪要」、不像专业汇总 | 自造壳、未对齐 simplified 体例 | 统一「代码审核汇总报告」；问题标「问题 N」 |
| 假 P0（`127.0.0.1`、`$ENV` 口令等） | enrich / 规则过猛 | 跳过回环与 RFC1918；环境变量占位不当事密钥 |
| 审查中途就「出完整报告」像有缓存 | 草稿 token / 壳提前推 UI | 审查中只推进度文案；终稿阶段再推报告 |
| 空行过多、不像报告 | `.reply` `pre-wrap` + `md()` 换行变 `<br>` 倍距 | `white-space: normal`；压缩 BR |
| 40 文件很慢 | 批太小 + 串行 | `BATCH_SIZE=8`，`PARALLEL_BATCHES=3` + `fresh_id` |
| 只有 P0、没有 P1/P2 | 严重度映射把 P1 抬成 high | 映射修正：P1→中危、P2→低危 |
| LLM 产出 0 条 / 像空审 | DeepSeek V4 `thinking` 占满 `max_tokens`，`content` 空 | 审码路径对 DeepSeek **关 thinking**；读 `reasoning_content`；抬高 tokens |
| 「一下子整段出来」假流式 | 同帧刷完 token | SSE 一行一条；前端队列约按行渲染 |
| 全 LLM 失败仍像「通过」 | `ok` 过松 | 全批失败 → `ok=false` +「审查不完整」 |

傍晚用户确认：**有真流式，报告质量打分 90+**。随后做批次 BUG/安全自检（失败闭口、thinking 仅 DeepSeek、HTTPS 公网 IP 降级为 P1、合并保留更高严重度、敏感 basename 加严等），并同步文档。

### 2.4 关键结论（可带走）

1. **先对齐主路径 UI，再抠报告质量**——确认卡 / 进度 / 终稿分阶段，比先堆 LLM prompt 省返工。  
2. **空 findings ≠ 通过**：必须有 enrich 补种 +「全 LLM 失败不得审核通过」。  
3. **模型能力坑要写进引擎**：V4 thinking 吃空 content 是系统性坑，不是「偶发幻觉」。  
4. **假流式会伤信任**：后端切行 + 前端队列才算「一行一行」。  
5. **Skill / Feature / Engine 三分法**在 DSH 上可行，且不破坏热插拔。
