# WorkBuddy 公司门禁叠层（冲 90 分 · 通用）

> 叠在 Viprasol 之上；**不替代**上游方法论。适用于任意语言/仓库，禁止写成某一演示项目的特例。

## 1. 必扫面（取码后必须覆盖或显式声明未覆盖）

在业务源码之外，只要仓库里存在，就必须审到（经 Bridge `file_contents` / `request_ide_read_files`），**不得默默跳过**：

| 类别 | 典型路径（按栈择一存在者） | 关注点 |
|------|---------------------------|--------|
| 依赖清单 | `pom.xml` / `build.gradle*` / `package.json` / `requirements*.txt` / `Pipfile` / `go.mod` / `*.csproj` / `Cargo.toml` | 过时/已知高危组件、锁定策略、多余权限依赖 |
| 运行配置 | `application*.yml|properties` / `appsettings*.json` / `.env.example` / `config/*` | 密钥明文、调试开关、管理端/actuator/metrics **过度暴露**、CORS/鉴权关闭 |
| 基础设施 | `Dockerfile*` / `docker-compose*.yml` / `*.tf`（若在采样内） | 以 root 跑、挂载密钥、开放端口 |
| 日志与隐私 | 源码中的日志调用 + 配置里的日志级别 | **脱敏**：token/密码/身份证/手机号是否进日志 |

若采样未带回上述文件：先 `request_ide_read_files` 补拉常见相对路径；仍没有则在「审核范围」写清 **未覆盖及原因**，不得假装已审。

## 2. 严重度加锋利（在 Viprasol Critical/High 之上的公司校准）

以下在**真实对外/多用户系统**中默认按 **P0（Critical）** 处理（须写触发条件；若能证明「仅本地玩具/无网络面」可降级并写明依据）：

- **认证/授权缺失**导致任意读写他人数据或管理接口裸奔（OWASP A01）
- **可导致数据损坏/覆盖**的竞态或非原子更新（错误 ID、丢失更新、覆盖别人记录）
- **可远程利用**的注入、RCE、明文密钥进仓

以下保持 **P1**，勿无依据抬到 P0：

- 仅教学演示且已在报告中标明「勿上生产」的反例方法（仍须列问题，但结论可写「移出 main / 加模块边界」）
- 纯风格、命名、可用 formatter 解决的问题 → P2/Nit

**数量自洽**：总览表里的 P0/P1/P2 条数必须等于正文实际条目数。

## 3. 修复建议可操作性（所有 P0/P1/P2 强制四段式）

正文每条问题必须按顺序写满以下四段（缺一视为不合格报告）：

1. **问题描述**：错在哪、为何危险、触发条件（输入/并发/配置）；含完整相对路径  
2. **问题代码**：从 `file_contents` 摘录的短代码块（含足够上下文）  
3. **修复建议**：怎么改、注意点、如何验证（Critical/High 须写验证步骤）  
4. **修复代码**：可粘贴替换的修复示例（禁止只写「建议加校验」「注意并发」）

涉及并发时：在修复建议/修复代码中写清 **原子边界**（例如 ID 分配与 `put`/`save` 必须在同一临界区或用 `compute`/`putIfAbsent`/事务）。

禁止空话修复：无代码、无 API 名、无「改哪几行」。

## 4. 验证方法（Critical / High / 等价 P0·P1 强制）

每条增加 **「如何验证」** 小节，通用写法：

- **复现**：最小请求/命令/步骤（例：HTTP 调用、单元测试骨架、并发脚本思路）
- **期望**：修复前失败现象 vs 修复后通过标准
- 安全类：给出**不造成真实破坏**的探测方式（如注入用无害 payload、鉴权用未登录 401）

报告壳中可在每条 P0/P1 末尾写 `**验证**: …`，或在文末加「验证清单」表（ID | 复现 | 通过标准）。

## 5. 与 Viprasol 输出的关系

- Verdict / Findings / What's good：仍跟上游。
- 中文壳 P0/P1/P2：映射见 `SKILL.md`；本文件负责「扫全、定准、可修、可验」。
