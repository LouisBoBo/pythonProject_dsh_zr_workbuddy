# 写码需求收集

面向 **本机写码 HITL** 的对话阶段（确认卡之前）。  
引擎 `discuss.py` 会出选项卡 / 确认卡；本 Skill 教 DSH Agent 如何引导用户、如何保真。

## 何时启用

- 用户要改代码、加页面、做报表 UI，但 **尚未** 点写码确认卡
- 需要澄清：目标模块、菜单/路由、接口、验收点
- **非写码任务不要读**（查数用 `mes_ask`）

## 核心目标

**少打字 → 结构化选项 → 完整需求摘要 → 人确认 → 才开工**

禁止跳过收集直接 `mes_code_dev_start`。

## 硬性规则（与引擎一致）

1. **逐字保留【原始诉求】**  
   用户第一句里的业务名词（如「员工工时报表」「报表中心菜单」）禁止改写成「通用列表页 CRUD」「消息中心」等。

2. **已有工程目录时不问技术栈**  
   选项聚焦本轮增量：侧栏入口 / 列表页 / 详情 / 配套 API / 样式微调。

3. **信息够时少轮询**  
   原始诉求 + 目标模块 + 勾选范围已齐 → 直接整理确认卡摘要，不要再出空泛选项。

4. **禁止声称已改代码**  
   讨论阶段只能说「整理方案 / 请确认」；真正改码在用户确认并由 Job 启动之后。

5. **requirement 摘要须含**  
   - 【原始诉求】  
   - 目标模块（如报表中心、消息中心）  
   - 菜单/路由/文件路径预期  
   - 接口路径（若涉及 CRUD）  
   - 验收点（用户能怎么验证）

6. **第 2 轮选项起，备注应写清**  
   用户勾选后若有歧义，在备注补一句，避免 LLM 自行脑补。

## 推荐对话流程

```text
用户说出改码诉求（保留原话作为 original_goal）
       ↓
仍模糊？ → 引导勾选：菜单 / 页面 / API / 其它
       ↓
够清晰？ → 口头或面板整理「写码确认卡」摘要
       ↓
用户点确认 / 明确口头同意
       ↓
才进入 zr-workbuddy-code-dev（mes_code_dev_start）
```

## 选项卡应覆盖的维度（参考）

| 维度 | 示例选项 |
| --- | --- |
| 本轮范围 | 侧栏入口、新列表页、改详情、配套接口 |
| 目标模块 | 报表中心、生产、消息、设置（以用户原话为准） |
| 数据来源 | 已有后端 API / 需新建路由 |
| UI 强度 | 纯逻辑 / 要专业界面（见 zr-workbuddy-ui-*） |

不要一次问超过 2 组；每组 3～6 个可勾选项即可。

## 常见翻车与纠正

| 翻车 | 纠正 |
| --- | --- |
| 「员工工时报表」→ 改做消息中心 CRUD | 回到原话，锁定 reports 模块 |
| 只写前端假数组 | 同轮要求后端路由 + api 封装（见 zr-workbuddy-coding-impl） |
| 用户只说「开始写吧」 | 先复述摘要 + 确认卡，再 start |
| 丢失 workspace | 追问本机工程绝对路径，或让用户在确认卡填写 |

## 与面板 / brief 的关系

- 面板会持久化 `codeDevBrief`（原始诉求、勾选历史）  
- Agent 侧也应 **在心里维护** 同一 brief，跨轮不丢原话  
- 最终传给 `mes_code_dev_start` 的 `message` 必须能通过引擎「泛化 CRUD / 关键词」校验
